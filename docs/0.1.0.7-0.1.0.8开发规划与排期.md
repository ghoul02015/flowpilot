## 一、版本关系与总体目标

### 1.1 两个版本的定位

| 版本 | 主题 | 核心问题 | 主要结果 |
| --- | --- | --- | --- |
| `0.1.0.7` | 性能与请求治理 | 固定周期、全局全量轮询；模型与硬件采集重复；慢请求可能重叠 | 建立统一轮询、取消、退避、缓存和写后失效机制，降低管理端无效请求与扫描开销 |
| `0.1.0.8` | 真实路由与 UI 信息架构收敛 | 页面由内部状态切换，缺少可刷新、可分享、可前进后退的页面地址；部分页面层级冗长 | 建立真实 URL、布局与路由级加载，迁移实例／任务详情，整理模型中心与系统管理，并完善移动端和可访问性 |

两个版本按顺序实施：`0.1.0.7` 先稳定数据刷新语义，`0.1.0.8` 再做路由和页面结构迁移。这样可以避免在路由改造期间同时重写数据请求逻辑，降低问题定位难度。

### 1.2 总体目标

1. 保持现有实例、镜像、模型、套装、任务、硬件和系统管理业务闭环不变。
2. 让自动刷新只发生在有数据消费需求、页面可见且满足活动条件的场景。
3. 将本地模型与 NAS 模型的扫描、错误和过期状态解耦。
4. 让主要页面、详情、页签和筛选状态拥有明确、可恢复的 URL。
5. 保持现有一级导航数量和主要操作入口，避免为“改版”而重构全部 UI。
6. 每个工作日都有可审查交付物，每个版本都有独立发布门禁与回滚路径。

### 1.3 明确不做

以下内容不属于这两个版本：

- 不新增 WebSocket 推送体系；现有 SSE 日志能力保持，其他数据先完成轮询治理。
- 不引入大型前端状态管理或数据请求框架。
- 不修改统一任务状态机、实例健康状态机或数据库 schema。
- 不改变模型下载、断点续传、SHA256、套装许可、实例关联和备份业务规则。
- 不做全量模型内容 hash 扫描。
- 不重建镜像任务体系，不新增工作流编辑器。
- 不提前实施恢复向导、服务端诊断包、主动告警中心、多机管理、RBAC／SSO、GPU 配额或资源调度。
- `0.1.0.7` 不做大规模 UI 重组；`0.1.0.8` 不承担新增业务功能。

## 二、已核对基线与实施前提

### 2.1 当前工程事实

1. 当前版本为 `0.1.0.6`。
2. 前端入口 `code/frontend/src/main.tsx` 已使用 `BrowserRouter`；`0.1.0.8` 应复用该入口，不重复添加路由器。
3. 当前页面切换主要由 `code/frontend/src/App.tsx` 内部的 `page / focus / token` 状态驱动。
4. 后端 `code/backend/internal/server/server.go` 已注册 `/api/v1/` 的未匹配 API 响应，并将 `/` 交给 `spa()`；静态文件不存在时回退到 `index.html`。

### 3.2 估算口径

1. 一个工作日只安排一个主要交付目标，避免将多个高风险模块同时标记为“完成”。
2. 开发完成不等于验收完成；单元测试、联调和问题修复包含在对应工作包中。
3. 测试从 D1 开始编写和补基线，不能等到 D9 或 D19 才首次介入。
4. 每天结束前更新：完成项、阻塞项、次日计划、指标变化和回滚风险。
5. 真实 GPU、NAS 或模型源不可用属于环境阻塞，不用“本机通过”替代环境验收。
6. 若出现范围新增，先评估是否进入后续版本，不直接压缩测试时间。
7. D10、D20 是发布评审点，不代表必须当天发布；门禁未通过则顺延。

### 3.3 完成定义

每个任务只有同时满足以下条件才可标记完成：

- 代码和配置变更已评审，并限定在本任务范围。
- 正常、空数据、慢请求、失败、恢复和取消路径均有验证。
- 新增或受影响的测试通过，无未解释的既有测试失败。
- 页面行为、API 契约或运维方式变化已更新对应文档。
- 没有将“界面能显示”误记为“业务闭环完成”。

# 第一部分：0.1.0.7 性能与请求治理

## 五、0.1.0.7 目标机制与数据规则

### 5.1 统一轮询语义

所有自动刷新统一满足：

1. 使用可等待异步执行的递归 `setTimeout`，上一次结束后再安排下一次。
2. 不使用无法感知异步请求完成的裸 `setInterval`。
3. 支持 `enabled`、页面可见性、立即执行、周期切换和手动刷新。
4. 组件卸载、路由离开、认证失效或条件关闭时清理计时器。
5. 请求支持 `AbortSignal`；不能取消的请求至少忽略过期响应，不能回写新页面状态。
6. 页面隐藏时暂停非必要轮询，恢复可见后立即刷新一次。
7. 失败按既定策略退避，不在错误状态下形成密集重试。
8. 同一数据源同一时间最多一个自动请求；手动刷新不得叠加并行请求。

### 5.2 默认刷新周期

| 数据／页面 | 活跃周期 | 空闲周期 | 额外规则 |
| --- | ---: | ---: | --- |
| 全局任务摘要 | 3 秒 | 30 秒 | 只为导航／顶栏获取摘要，不拉完整任务列表 |
| 实例列表：首页／实例页 | 状态迁移时 3 秒 | 5 秒 | 非相关页面不维持同频率列表刷新 |
| ComfyUI 队列 | 运行实例 5 秒 | 不运行时停止 | 仅相关页面消费时执行，失败实例独立处理 |
| 健康版本 | — | 60 秒 | 登录后加载，写操作不触发无意义版本刷新 |
| 首页硬件 | — | 5 秒 | 页面隐藏时暂停 |
| 硬件页 | — | 2 秒 | 与首页请求共享后端短时采集合并 |
| 模型页 | — | 60 秒 | 其他页面不周期拉取全量模型 |
| 任务页 | 2 秒 | 15 秒 | 有排队／运行／暂停等活动状态时短周期 |
| 镜像任务 | 2 秒 | 停止或低频列表刷新 | 仅活跃任务期间短周期 |
| 套装列表安装状态 | 3 秒 | 无安装时停止短周期 | 只追踪相关安装 |
| 套装安装向导 | 2.5 秒 | 非活动状态停止 | 关闭向导必须取消 |
| 实例详情健康 | 5 秒 | 页面不可见暂停 | 详情关闭后停止 |
| 实例详情事件 | 15 秒 | 页面不可见暂停 | 手动操作后可主动刷新 |

失败退避采用 3／5／10／30／60 秒档位。业务操作后的主动刷新不等长周期；恢复联网、恢复可见或手动刷新时可重置退避。

### 5.3 业务刷新事件

建议新增 `code/frontend/src/lib/refresh-events.ts`，统一以下事件语义：

| 业务变化 | 需要失效／刷新的数据 |
| --- | --- |
| 下载创建、暂停、恢复、取消、删除 | 任务摘要、任务列表、模型列表中的任务投影 |
| 本地导入完成 | 模型列表、任务摘要、任务列表 |
| 模型删除、本地化完成 | 本地／NAS 模型缓存、模型列表、实例模型关联 |
| 实例创建、启动、停止、重启、删除 | 实例列表、详情、健康、首页摘要 |
| 镜像拉取、构建、导入、删除、清理 | 镜像列表、镜像任务、磁盘占用、相关任务摘要 |
| 套装预检、安装、暂停、恢复、取消、关联 | 套装状态、安装进度、模型与实例相关数据 |
| 网络存储配置变化 | NAS 状态、模型网络仓库缓存、页面错误／过期状态 |

事件只表达“哪些数据过期”，不把所有数据重新塞入全局 store。页面只订阅自己消费的数据。

## 六、0.1.0.7 工作包与开发步骤

### WP07-00：冻结基线与测试口径（D1）

**责任：测试主导，前端、后端配合。**

1. 固定 `0.1.0.6` 基线提交、配置和测试数据。
2. 为 S0～S5 编写请求记录模板，区分自动、手动和写后刷新请求。
3. 记录各页面 10 分钟请求数、模型扫描次数、硬件采集次数和关键接口耗时。
4. 对实例、下载、导入、镜像、套装、备份、安全和审计跑现有回归。
5. 明确性能比较必须使用同场景、同数据规模和同浏览器可见状态。

**交付物：**基线记录、场景数据准备步骤、现有问题清单、性能对比模板。

**验收：**后续每个指标都能追溯到场景与原始记录，不使用估计值充当实测值。

### WP07-01：统一前端轮询与 API 取消（D2）

**建议新增／修改文件：**

- 新增 `code/frontend/src/hooks/use-polling.ts`。
- 新增 `code/frontend/src/lib/refresh-events.ts`。
- 修改 `code/frontend/src/api.ts` 或现有 API 模块的实际位置，以工程当前导出方式为准。
- 新增轮询器与刷新事件的单元测试。

**开发步骤：**

1. 定义轮询输入：执行函数、周期、`enabled`、立即执行、可见性策略和退避策略。
2. 定义输出：刷新、停止、当前执行状态、最后成功／失败时间和错误信息。
3. 用递归计时保证请求完成后才安排下一次。
4. 在 effect 清理中同时处理计时器和 AbortController。
5. 处理页面隐藏、恢复、手动刷新和周期变化。
6. 为 API 请求增加可选 signal 传递，避免每个页面自行实现取消。
7. 明确被主动取消的请求不展示错误 toast，不覆盖在线状态。
8. 编写假计时器测试，覆盖慢请求、卸载、隐藏、恢复和失败退避。

**依赖：**WP07-00 的口径。

**验收：**同一数据源无重叠；组件卸载后无状态回写；隐藏时非必要请求为零；恢复后立即刷新；失败不形成紧循环。

### WP07-02：全局数据与轻量任务摘要（D3）

**建议修改文件：**

- `code/frontend/src/App.tsx`
- `code/frontend/src/api.ts`
- `code/frontend/src/types.ts`
- 后端统一任务查询与 `code/backend/internal/server/server.go` 中对应注册位置
- 任务相关后端测试

**开发步骤：**

1. 后端新增 `GET /api/v1/tasks/summary`，通过 SQL 聚合返回导航所需计数和活动状态。
2. 摘要保持轻量，不嵌入完整任务、日志或镜像输出。
3. 明确计数口径：排队、运行、暂停、失败、完成等状态如何分类。
4. 前端将实例、模型、完整下载列表和健康版本从单一全局 3 秒轮询中拆出。
5. 顶栏只保留其实际消费的摘要与主机信息。
6. 页面级数据交由对应页面加载；跨页写操作通过刷新事件通知。
7. 保持未登录和初始化状态不产生业务轮询。
8. 保持全局 401 处理、后端离线和空态语义。

**接口输出要求：**字段名和分类以现有任务状态为准；不得为计数新增数据库表或改变 schema。

**验收：**导航角标不依赖全量任务请求；活动摘要不超过 3 秒，空闲约 30 秒；SQL 聚合结果与完整列表同源一致。

### WP07-03：模型缓存、扫描合并与 NAS 隔离（D4～D5）

**涉及范围：**模型仓库扫描、模型读取 API、网络存储状态、写操作失效及相应测试。具体实现文件以当前模型服务和 API 分层为准，不为迎合规划强行移动既有代码。

**D4 开发步骤：**

1. 将本地仓库与网络仓库缓存项、锁、错误和更新时间拆开。
2. 本地缓存默认有效期 60 秒，NAS 默认 120 秒。
3. 同一仓库扫描进行期间，后续读取复用进行中的结果，避免并发重复扫描。
4. 扫描结果包含来源、更新时间、扫描状态和错误信息，不只用空数组表达失败。
5. 本地与 NAS 并行或独立读取，NAS 失败时保留本地结果。
6. 为慢扫描和超时建立可观测日志，但不记录敏感路径以外的无关信息。

**D5 开发步骤：**

1. 下载、导入、删除、本地化和套装相关写入后，仅失效受影响来源。
2. 网络存储配置变化只主动失效 NAS 缓存，并触发按需刷新。
3. NAS 断开后显示不可用或数据过期，不把旧数据伪装为刚扫描成功。
4. NAS 恢复后允许手动刷新和后续周期刷新恢复。
5. 前端模型页根据元数据分别展示本地与 NAS 状态。
6. 非模型页不再周期拉取全量模型。
7. 完成并发、超时、缓存失效和恢复测试。

**依赖：**WP07-01 的取消语义；WP07-02 的全局请求拆分。

**验收：**模型页空闲扫描不短于 60 秒；非模型页无全量周期扫描；同来源无并发重复扫描；NAS 故障不影响本地；写后无需等待长周期即可看到正确结果。

### WP07-04：硬件采集合并与负缓存（D6）

**涉及范围：**硬件报告服务、`code/backend/internal/server/server.go` 的硬件接口、首页和硬件页前端请求。

**开发步骤：**

1. 对短时间内并发的硬件采集进行合并，调用方共享同一次结果。
2. 区分主机、CPU、内存与 GPU 子结果，避免一个子项失败导致所有信息消失。
3. `nvidia-smi` 不存在等持续性错误使用 60 秒负缓存，避免每次请求重复执行失败命令。
4. 临时超时与“命令不存在”分开记录；恢复条件清晰。
5. 前端首页采用 5 秒、硬件页采用 2 秒，并接入可见性和取消。
6. 保证创建实例向导所需 GPU 名称仍可获取，失败时提供明确空态与重试。
7. 添加并发采集、无 GPU、命令缺失和恢复测试。

**依赖：**WP07-01。

**验收：**并发请求不导致并发重复执行硬件命令；持续缺失命令不会在每次页面刷新时重复调用；GPU 数据错误不拖垮整个管理端。

## 十四、风险、控制与回滚

### 14.1 主要风险

| 风险 | 早期信号 | 控制措施 |
| --- | --- | --- |
| 降频导致状态陈旧 | 操作已完成但页面长期不更新 | 写后主动失效；活跃状态短周期；恢复可见立即刷新 |
| 请求取消误报离线 | 切换页面出现错误 toast 或离线 | 区分主动取消与真实网络失败 |
| 模型缓存返回旧数据 | 删除后文件仍出现 | 来源级主动失效；显示更新时间与扫描状态 |
| NAS 故障级联 | 本地模型也为空或超时 | 独立缓存与错误；本地结果单独返回 |
| 摘要与列表不一致 | 角标数量和任务页不同 | 同一状态口径与 SQL 来源；自动化对比 |
| 路由迁移丢操作 | 原弹窗按钮在详情无入口 | 迁移前建立操作映射，逐项 E2E |
| 认证重定向循环 | setup/login/dashboard 反复跳转 | 明确状态表；集中门卫；深链接测试 |
| SPA 吞掉 API 404 | 前端收到 HTML 解析错误 | 保留 API 专用未匹配处理器；接口测试 |
| 多页签重复轮询 | 模型或系统请求倍增 | 仅活动页签挂载；不可见面板不轮询 |
| 窄屏隐藏关键操作 | 375 px 无法删除、返回或查看日志 | 提供折叠／菜单等可达方式，不直接隐藏 |
| 范围膨胀 | RC 前加入告警、恢复或多机 | 变更评审，移入后续版本 |

### 14.2 `0.1.0.7` 回滚

1. 保留上一版本前后端可部署产物和配置说明。
2. 新增任务摘要为增量接口，回滚前端后不得依赖该接口才能运行。
3. 缓存与负缓存不修改数据库 schema，回滚不需要数据降级。

5. 回滚后检查实例、模型、镜像、任务、硬件和系统主流程，并重新记录请求行为。

2. 路由改造不涉及数据迁移，回滚不应要求清空数据库或模型仓库。

- [ ] 文件路径在动手前与当前工程再次核对；规划中的新增文件不是现有文件声明。
- [ ] 当天改动限定在工作包范围，跨版本需求单独记录。
- [ ] 任何接口或 URL 契约变化先更新测试，再迁移调用方。

### 16.2 测试负责人

- [ ] 基线和对比使用同环境、同数据和同可见状态。
- [ ] 慢请求、失败、取消和恢复与正常路径同等覆盖。
- [ ] 真实 GPU、NAS、大模型库和 Docker 结果单独记录。
- [ ] RC 之后只修复阻断问题，新增需求进入后续版本。

### 16.3 产品／发布评审

- [ ] `0.1.0.7` 只解决性能与请求治理。
- [ ] `0.1.0.8` 只解决路由与信息架构，不借机新增业务子系统。
- [ ] 一级导航仍为现有 7 个入口，实例、模型、任务和系统的调整符合本文范围。
- [ ] 性能结论仅针对管理端，不解释为模型推理或出图性能。
- [ ] 所有“完成”均有测试证据；未验证环境明确披露。

## 十七、排期结论

在 1 名前端、1 名后端、1 名可兼职测试并行的参考配置下，两个版本按 20 个工作日规划：

- D1～D10：完成 `0.1.0.7` 的机制建设、页面迁移、性能验证与发布评审。
- D11～D20：完成 `0.1.0.8` 的真实路由、页面迁移、UI 收敛、全量回归与发布评审。
- D10 和 D20 均为门禁节点，未通过则顺延，不以压缩回归换取计划日期。
- 单人串行、真实 GPU／NAS 环境不可用或既有回归存在大量失败时，需要重新估算。

本文是两版本合并后的执行基线。后续实际开发应以工作包和验收项为跟踪单位，不以文档完成代替功能完成。
