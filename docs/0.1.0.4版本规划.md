## 一、版本定位

### 1.1 一句话目标

在现有模型中心上增加“模型组合套装”能力，让管理员能够按场景完成**依赖查看、硬件预检、许可确认、整组下载／导入、完整性校验、实例关联和人工验收记录**，不再逐个寻找 H3 模型文件。

### 1.2 当前基线判断

项目 `VERSION` 已为 `0.1.0.3`，因此本规划不再采用旧文档中插入 `0.0.9.x` 版本列车的方案。[VERSION](kimi-cite://md-line?path=%2FUsers%2Fzhouyazhou%2FDocuments%2Fkimi%2F%E6%85%A7%E6%B5%AA%E6%99%BA%E7%AE%97comfyui%E7%AE%A1%E7%90%86%E5%B9%B3%E5%8F%B0%2FVERSION&line=1&text=0.1.0.3 "citation")

当前可直接复用：

- 模型目录、ModelScope／HF 双源、URL 下载、本地导入、断点续传和 SHA256。
- SQLite 迁移、统一任务、认证与审计。
- 实例模型符号链接关联，无需重建实例。
- GPU／统一内存采集与硬件兼容性检查。
- ComfyUI 固定版本构建和镜像版本元数据。

`0.1.0.3` 已在 Spark 成功构建固定 ComfyUI `v0.45.0` 的 cu130 镜像，为 H3-Image 提供了版本基础；但模板包版本、量化算子和真实 H3 工作流仍需单独验收。[0.1.0.3](kimi-cite://md-line?path=%2FUsers%2Fzhouyazhou%2FDocuments%2Fkimi%2F%E6%85%A7%E6%B5%AA%E6%99%BA%E7%AE%97comfyui%E7%AE%A1%E7%90%86%E5%B9%B3%E5%8F%B0%2Fcontext%2Fchanges%2F0.1.0.3.md&line=59&text=%7C%20cu130%20%E6%9E%84%E5%BB%BA%20 "citation")

### 1.3 本版交付边界

**本版做：**

1. 五个 H3 套装 manifest 及依赖关系。
2. 套装列表、详情、安装向导和状态展示。
3. 硬件匹配建议、磁盘预检、ComfyUI 版本提示。
4. 许可展示、确认记录和审计，不默认附带模型权重。
5. 串行整组下载／离线导入、失败续装、重复提交保护。
6. 复用现有实例模型关联，实现套装一键关联。
7. 人工验收记录与 JSON 导出，明确“人工记录”而非自动认证。
8. 测试、文档、发布说明与回滚方案。

**本版不做：**

- 不自动调用 ComfyUI Prompt API 运行工作流，不自动生成性能认证。
- 不随 FlowPilot 发布包分发模型权重，不默认出厂预装。
- 不改造实例创建向导，不新增“从套装创建实例”流程。
- 不做多 GPU 并行、显存叠加、SGLang／vLLM 服务化部署。
- 不做提示词编辑器、工作流编辑器、电商或短视频业务应用。
- 不自动判断商业授权，不将许可复选框当作法律授权。
- 不承诺 4090／5090 offload 性能，不承诺本地 H3 原生 2K。
- 不顺带修改 PyTorch 锁定策略或重做镜像构建系统；现有镜像问题独立处理。

## 三、套装 Manifest 设计

### 3.1 数据原则

- manifest 随 FlowPilot 版本固定，带独立 `bundleVersion` 和内容 checksum。
- 模型文件不写入 FlowPilot 仓库，只保存来源、路径、大小、revision、SHA256、许可和工作流引用。
- 每个下载源单独记录 revision 与 hash；只有内容一致才能互为主备源。
- 不使用永久 `main` 作为出厂坐标；实现时锁定实际 revision。
- 官方未提供hash时，以下载后完整文件的 SHA256 为实测结果，经复核后写入 manifest，不能编造。
- 文件大小统一保存字节数；UI 再格式化为 GB／GiB，禁止混用不同来源的约数做精确容量结论。
- manifest 内硬件状态默认 `candidate` 或 `experimental`，`certified` 只能来自慧浪后续审核发布。

### 3.2 必备字段

```text
Bundle
  id / version / name / summary / capability / releaseChannel
  requiredComfyUI / requiredTemplatePack
  variants[]
  items[]
  hardwareRules[]
  workflows[]
  license
  certificationByHardware[]

BundleItem
  key / role / required / category / fileName
  sources[repo, revision, filePath, sizeBytes, sha256]
  conflicts[] / dependsOn[] / optionalGroup

License
  name / sourceURL / snapshotDate / reviewStatus / noticeRequired
  commercialUIRequired / acknowledgementVersion
```

### 3.3 版本与升级

- `0.1.0.4` 发布首版 `minimax-h3-bundles/v1`。
- 本版不做在线自动更新 manifest，避免未审核内容悄悄变更。
- 后续文件、许可或硬件认证变化通过新 `bundleVersion` 发布。
- 已有下载文件不因 manifest 更新自动删除或替换。
- 新旧版本文件 hash 不一致时显示“有新版”，由管理员另起升级计划。

## 四、后端实施规划

### 4.1 新增套装领域模块

建议新增独立 `internal/bundle` 模块，不把全部逻辑继续塞入 `catalog` 或 `server`：

1. 加载并校验内置 manifest。
2. 计算套装必需项、可选项、互斥组和总字节数。
3. 对照本地／NAS 模型、当前下载任务计算每项状态。
4. 生成硬件、镜像、磁盘和许可预检结果。
5. 创建和恢复套装安装计划。
6. 串行调用现有下载／导入管理器。
7. 汇总子任务状态并写入统一任务。
8. 生成套装模型关联计划，调用现有实例模型链接能力。
9. 保存许可确认和人工验收记录。
10. 导出不含敏感信息的验收 JSON。

### 4.2 状态模型

文件状态：

```text
missing / downloading / paused / verifying / present / hash_mismatch / conflict
```

套装安装状态：

```text
not_installed / partial / queued / installing / paused
files_ready / failed / cancelled
```

附加状态独立展示：

- 实例关联：未关联／部分关联／已关联。
- 人工验收：未记录／记录通过／记录失败。
- 慧浪认证：待认证／实验／已认证（只能由审核 manifest 给出）。

**禁止把“文件下载完成”直接显示为“模型可用”或“慧浪认证”。**

### 4.3 下载与导入编排

- 每个“套装＋变体＋目标仓库”同时只允许一个活动安装计划。
- 默认一次只下载一个大文件，完成后启动下一个，避免数份 20 GB 文件并发占满带宽和磁盘。
- 已存在且大小／hash 匹配的项自动跳过。
- 已存在的普通下载任务可被识别，但不能被两个套装计划重复控制。
- 同名不同 hash 进入冲突状态，不覆盖、不自动改名伪装成功。
- 暂停保留 `.part` 和计划；继续时从缺失项及断点恢复。
- 服务重启后，活动计划转为“待继续”，不永久显示安装中。
- 取消计划保留已入库文件，由用户决定是否沿用现有删除流程清理。
- 离线导入仍限制在现有 `/data/import` 白名单，逐文件匹配 manifest，不开放任意宿主机路径。
- 任一必需项失败时套装为“部分／失败”，可只重试失败项；可选 Turbo 失败不影响基础文件齐备判定，但必须显示原因。

### 4.4 硬件匹配规则

| 当前环境 | S1／S2 | S3 | S4／S5 | UI 结论 |
| --- | --- | --- | --- | --- |
| DGX Spark 128 GB 统一内存 | 推荐认证候选 | 推荐认证候选 | 实验 | 可预检，不显示性能承诺 |
| RTX PRO 6000 Blackwell 96 GB | 优先认证候选 | 推荐认证候选 | 实验／待 x86 实测 | 可预检，显示待认证 |
| RTX 4090／5090 | 实验 offload | 实验 | 不建议 | 不阻断下载，强警告 |
| 其他 NVIDIA | 未知 | 未知 | 未知 | 显示“未评估”，不猜测 |
| 无 GPU／采集失败 | 不建议 | 不建议 | 不建议 | 允许仅下载资产，关联运行前警告 |

- 硬件匹配只用于建议，不把“文件大小之和”当显存需求。
- 不用多卡显存总和推导单实例可运行性。
- Spark 使用共享内存口径，不重复累计显存与系统内存。
- 当前项目既有记录中 x86 NVIDIA 多卡尚未完成总验收，因此 PRO 6000 不得预先显示“已认证”。[0.1.0.0](kimi-cite://md-line?path=%2FUsers%2Fzhouyazhou%2FDocuments%2Fkimi%2F%E6%85%A7%E6%B5%AA%E6%99%BA%E7%AE%97comfyui%E7%AE%A1%E7%90%86%E5%B9%B3%E5%8F%B0%2Fcontext%2Fchanges%2F0.1.0.0.md&line=38&text=%7C%20x86%20NVIDIA%20%E5%A4%9A%E5%8D%A1%20 "citation")

### 4.5 镜像与版本预检

- H3 基础工作流：ComfyUI `0.30.0+`。
- H3-Image：ComfyUI `0.45.0+`、模板包 `0.11.104+`。
- S5 统一按较高的 `0.45.0+` 检查。
- 优先读取现有 `flowpilot.comfyui.version`、commit、镜像 digest 等元数据。
- 老镜像没有版本信息时显示“无法确认”，不自动视为通过。
- 当前已构建 `v0.45.0` 只代表 Core 版本满足；模板包和实际节点仍需检测或记录人工验收。
- 本版只提示需要更换／构建镜像，不自动触发长时间镜像构建。

### 4.6 磁盘预检

分别计算：

- 缺失文件剩余下载字节。
- 已下载分片和已完成文件，避免重复计数。
- 下载、移动、导入复制所需的临时空间。
- 用户配置的输出预留和安全余量。
- NAS 已存在文件与本地化需求的区别。

空间不足可阻断“开始安装”，但不阻断查看清单；警告与阻断原因必须列出具体数值和可释放建议。

### 4.7 许可与审计

- 默认许可审核状态为 `needs_review`，不显示“可商用”。
- 开始下载／导入前需要确认“已阅读模型许可与使用限制”。
- 记录操作者、套装、bundleVersion、许可版本／快照日期、时间和交付方式。
- H3-Image 在套装卡片、详情和关联实例区域准确显示 `MiniMax-H3-Image` 名称。
- 许可确认接口不能由前端单独伪造，后端校验确认版本与当前 manifest 一致。
- 审计不记录模型下载签名 URL、Token 或其他凭据。
- “慧浪预装权重”不在本版开放，因此不生成任何出厂权重包。

### 4.8 人工验收记录

字段：

- 套装与 bundleVersion、安装计划 ID。
- 主机型号、GPU UUID／型号、统一或独立内存模式。
- 实例、镜像 digest、ComfyUI／模板包版本。
- 验收档位：4 MP／16 MP、5／10／15 秒、参考数量、Turbo 选项。
- 结果：通过／失败／部分通过。
- 冷启动、首次生成、暖机耗时和资源峰值为可选手工填写字段，必须注明“人工记录”。
- 输出检查、离线运行、重启恢复、备注、操作者和时间。

导出的 JSON 不包含账号、Cookie、内网凭据或签名 URL。人工记录不能直接改写“慧浪认证”。

## 五、数据库与 API 规划

### 5.1 SQLite 增量迁移

只新增表，不修改历史实例和模型数据：

| 表 | 用途 |
| --- | --- |
| `bundle_installs` | 安装计划、套装版本、变体、状态、当前项、错误、创建／完成时间 |
| `bundle_install_items` | 每个文件项、来源、目标、状态、下载／导入任务 ID、hash、错误 |
| `bundle_license_confirmations` | 许可版本、确认人、确认时间、交付方式 |
| `bundle_acceptances` | 人工验收环境、档位、结果、指标 JSON、备注和操作者 |

要求：

- 迁移幂等、有 checksum、升级前自动沿用现有 SQLite 快照。
- 套装列表状态主要由 manifest＋仓库扫描＋安装记录计算，避免重复维护一套文件事实。
- 索引覆盖套装 ID、计划状态、任务 ID 和验收时间。
- 回滚到 `0.1.0.3` 时保留新表但不使用，不删除用户模型和验收历史。

### 5.2 API 草案

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/v1/model-bundles` | 套装卡片、状态、总量和当前硬件摘要 |
| `GET /api/v1/model-bundles/{id}` | 文件、工作流、许可、硬件、安装与验收详情 |
| `POST /api/v1/model-bundles/{id}/preflight` | 按变体、来源、实例生成预检，不产生写操作 |
| `POST /api/v1/model-bundles/{id}/installs` | 创建幂等安装计划 |
| `GET /api/v1/model-bundles/{id}/installs/{installId}` | 计划与逐项进度 |
| `POST /api/v1/model-bundles/{id}/installs/{installId}/{action}` | pause／resume／cancel／retry |
| `POST /api/v1/model-bundles/{id}/link` | 将文件齐备项关联到现有实例 |
| `POST /api/v1/model-bundles/{id}/acceptances` | 新增人工验收记录 |
| `GET /api/v1/model-bundles/{id}/acceptances` | 分页查询历史 |
| `GET /api/v1/model-bundles/{id}/acceptances/{acceptanceId}/export` | 导出脱敏 JSON |

所有写接口沿用认证、CSRF／Origin、参数校验、审计和操作锁；预检不得偷偷创建下载、目录或实例链接。

## 六、前端页面与交互规划

### 6.1 模型中心结构

本版只在模型中心增加两个主标签：

```text
本地仓库｜组合套装
```

- 保留当前“添加模型”弹窗和模型市场，不顺带重构在线来源。
- 本地仓库页面及搜索、批量删除、NAS 本地化保持原行为。
- 组合套装页使用独立数据请求，不与每 3 秒模型刷新互相触发全量重载。
- PageHeader 文案增加“按场景整组部署和验收”，主操作由套装卡片承担。

### 6.2 套装列表页

五张卡片，桌面双列、宽屏三列、移动单列。每张卡片显示：

- 准确模型名称与套装名称。
- 图像／视频／音频能力标签。
- 必需文件数、可选扩展数、实际字节总量。
- 当前安装进度与文件齐备状态。
- 当前主机匹配结论。
- 许可状态和认证状态，二者分开。
- 主按钮：查看／预检安装／继续安装／查看结果。

筛选只保留：全部／图像／视频／图视一体／可安装／实验。  
不在首版增加评分、销量、艺术效果排行或无依据的“流畅”标签。

### 6.3 套装详情抽屉

桌面使用宽抽屉，移动端全屏，包含五个子页：

| 子页 | 内容 | 主要操作 |
| --- | --- | --- |
| 概览 | 场景、能力边界、认证与安装状态 | 预检安装、打开关联实例 |
| 文件与依赖 | 必需／可选、大小、来源、revision、hash、本地状态 | 选择变体、查看冲突、重试失败项 |
| 硬件与工作流 | 当前硬件匹配、镜像要求、官方模板、验收档位 | 重新预检、跳转镜像中心 |
| 许可 | 许可链接、审核状态、NOTICE 提示、确认历史 | 阅读并确认新版本许可 |
| 验收记录 | 环境、参数、结果、人工指标和备注 | 新增记录、导出 JSON |

所有标签在数据失败时保留抽屉上下文，提供错误码和重试，不回退成空白卡片。

### 6.4 四步安装向导

1. **选择内容：** 套装变体、Turbo／全参考扩展、在线源或离线导入。
2. **环境预检：** GPU／内存模式、磁盘、ComfyUI／模板、已有文件和冲突。
3. **许可确认：** 许可链接、版本、交付边界和确认项。
4. **确认执行：** 总下载量、串行计划、目标路径摘要、关联实例选项。

- 上一步数据变化后，下一步必须重新预检。
- 提交按钮 loading 之外，服务端仍以安装锁防重复。
- 警告可确认继续，磁盘不足、hash 冲突、许可版本不匹配等明确问题阻断。
- 完成后关闭向导但保留任务入口，不把“已创建任务”写成“安装完成”。

### 6.5 安装进度与失败状态

- 详情页显示总进度、当前文件、已完成／总字节、当前子任务。
- 每个文件显示下载、暂停、校验、完成、失败或冲突。
- 支持暂停／继续／取消／只重试失败项，按实际能力展示按钮。
- 服务重启后的计划显示“待继续”，不伪造运行状态。
- 可选扩展失败与必需项失败使用不同摘要。
- 取消时明确已完成模型保留，不自动删除。

### 6.6 实例模型关联

- 只有必需文件齐备才显示“关联基础套装”主按钮。
- 实例选择器显示应用健康、模型链接支持情况、镜像版本和 GPU。
- 关联前展示新增项，不默认移除实例已有模型。
- 后端读取当前链接并合并，避免前端旧数据覆盖其他修改；发生冲突要求刷新。
- 旧实例不支持模型链接时提示重建／升级路径，不假装成功。
- 可选 Turbo 可独立补充关联。
- 关联成功后显示“文件已关联”，仍需在 ComfyUI 中运行工作流验证。

### 6.7 硬件管理小入口

不重建硬件页，只新增一个轻量“模型套装匹配”卡片：

- 显示推荐认证候选、实验和未知数量。
- 列出最多三项当前相关套装及原因。
- 点击跳转模型中心的组合套装标签并带入硬件筛选。
- 无 GPU／采集失败时保留最后成功数据并标记过期。

### 6.8 通用 UI 与性能

- 卡片刷新使用骨架屏，已有内容不闪空。
- 空态区分从未安装、筛选无结果、接口失败和离线。
- 状态不只依赖颜色，认证、人工验收和文件状态使用不同图标与文字。
- 大文件列表可折叠，长路径省略但可复制；移动端无页面级横向滚动。
- 页面打开不触发全量 SHA256；hash 只在下载完成或明确校验任务中执行。
- 套装列表缓存当前扫描结果，避免每个卡片重复扫盘和重复硬件采集。
- 所有容量、时间、revision 和错误码格式与现有平台统一。

## 七、实施步骤

### 步骤 1：冻结资产与边界

- 确认五个套装 ID、必需／可选文件、官方源和备用源。

- 演练从 `0.1.0.3` 升级、重复迁移和回滚。

### 步骤 3：预检与安装编排

- 完成本地状态计算、硬件／镜像／磁盘／许可预检。
- 完成串行下载、离线导入、暂停恢复、失败重试和取消。
- 接入统一任务与审计，防重复提交。
- 完成实例关联合并和冲突保护。

### 步骤 4：前端套装闭环

- 全量后端、前端和 E2E 回归。

## 九、性能、安全与回滚

### 9.1 性能目标

- 套装安装默认单文件串行，避免无界并发。
- 套装列表不触发全量 hash，不为五张卡片重复扫描目录。
- 大模型 hash、导入和校验继续流式执行。
- 安装状态写入按状态变化和合理进度间隔执行，不每个分片写 SQLite。
- 页面不可见时复用现有降频策略，不新增独立高频轮询。

### 9.2 安全目标

- 所有新写 API 需认证、CSRF／Origin 和服务端参数校验。
- 下载继续沿用 SSRF 防护与源白名单，备用源重定向逐跳检查。
- 文件路径必须来自 manifest 或受控导入映射，拒绝路径穿越和符号链接逃逸。
- 模型删除继续复用运行实例引用保护。
- 许可、验收和诊断导出不含 Token、Cookie、NAS 凭据或签名 URL。
- manifest 更新不在后台静默执行，避免供应链内容漂移。

### 9.3 回滚

1. 升级前沿用现有 SQLite 自动快照。
2. 健康门失败回滚 `flowpilot-web:0.1.0.3`。
3. 新增表保留，旧版本不读取；不反向删除安装和验收历史。
4. 已完成模型文件和实例链接不属于管理面回滚删除范围。
5. 若需撤销错误关联，按实例生成关联预览并保留用户原有模型，不做全量清空。
6. 发布说明明确数据库兼容与回滚行为，并实际演练一次升级→安装套装→回滚→文件与记录保留。

## 十、Go／No-Go 发布门槛

以下全部为“是”才能发布 `0.1.0.4`：

- 五个 manifest 的依赖、来源、revision、大小、hash 和许可字段是否完整且经复核？
- S1～S3 是否能完成预检→许可→安装→校验→关联闭环？
- S4／S5 是否始终显示实验状态，没有误导销售文案？
- 是否不会把文件齐备或人工验收记录自动显示为慧浪认证？
- 暂停、续传、服务重启、失败重试、重复提交和取消是否有测试证据？
- 图像 INT8 与视频 NVFP4 编码器是否未被错误去重？
- 是否没有默认附带任何模型权重？
- 数据库升级、快照和回滚是否实测，模型与历史记录是否保留？
- 后端、前端、本机 E2E 是否全量通过，本地模型和实例功能是否零回归？
- 发布文档是否明确硬件候选、人工验收和自动认证的区别？
- 发布包是否不含权重、Token、内网凭据和测试资产？

任何一个必需项不满足，继续作为 RC，不通过隐藏状态或降低文案标准强行发布。

## 十一、后续版本衔接

以下内容不阻塞 `0.1.0.4`，后续单独规划：

1. 自动运行官方工作流、读取队列和输出，生成自动验收报告。
2. 经审核的硬件认证 manifest 更新和出厂验收报告整合。
3. 从套装创建实例、镜像自动选择与缺失镜像构建计划。
4. 模型套装版本升级、差异比较、回滚和多机分发。
5. 法务放行后的客户自带权重交付与慧浪预装权重 SKU。
6. SGLang／vLLM 独立服务化模板及 H200／B300 多卡路线。
7. 电商视觉、短视频广告等独立业务场景包。

## 十二、版本完成定义

`0.1.0.4` 完成不等于“五个模型套装已经在所有硬件上跑通”，而是：

> FlowPilot 已能以可追溯、可恢复、许可有记录的方式交付套装文件和实例关联，并且清楚区分当前硬件建议、文件状态、人工验收和慧浪认证。

这样才能用一个相对独立的小版本形成产品价值，同时不把自动工作流、硬件认证和权重合规风险拖进同一次发布。
